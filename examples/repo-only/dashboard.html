To-be architecture

  • All document templates declare the content language. Assistive technology uses it to choose pronunciation and translation tools use it to detect language.
  • Image components require alt text by type or lint rule. Text alternatives are a baseline accessibility requirement (WCAG 1.1.1).
  • Each critical journey has an end-to-end test that gates deployment. Only executed journeys provide runtime evidence that the product works for users.
  • Lockfile committed; CI installs with a frozen lockfile. Reproducible builds are a precondition for meaningful testing and rollback.
  • Unit and integration tests run with one command locally and in CI. Tests turn 'it seemed to work' into repeatable evidence.
  • Every pull request runs build, lint and tests automatically. CI is where tests become a gate rather than a suggestion.
  • README documents setup, environment and test commands. Reproducible setup is a precondition for testing and handover.
  • Runtime version declared once and used by CI and hosting. Runtime drift causes works-on-my-machine failures.
  • Type check and lint run in CI. Cheap automated checks catch common defects introduced by fast iteration.
  • All dependencies declared with bounded ranges; updates via reviewed pull requests. Bounded versions make dependency changes reviewable events.
  • Errors and traces flow to a monitored backend with alerts. You cannot fix what you cannot see; this is a precondition for launch watch.
  • Every schema change is a reviewed migration applied by the deployment pipeline. Versioned migrations make data changes reviewable, repeatable and reversible.
  • Secrets live only in the hosting provider's secret store and are read server-side at runtime. A committed secret must be assumed leaked; deleting it from the latest commit does not revoke it. Alternatives: Use a secret manager (cloud KMS / Vault / Doppler) instead of plain environment variables.
  • Client calls the product's own server API; privileged keys stay server-side. Bundlers inline public-prefixed variables into JavaScript that every visitor downloads. Alternatives: Use row-level security with the publishable/anon key for direct database access from the client.
  • Only a placeholder .env.example is tracked. Environment files are where real secrets live during development.
  • Security contact published and monitored. Responsible disclosure needs a known channel.
  • Data never concatenated into code, markup or queries. Injection remains a top cause of breaches.
  • CORS allow-list per environment. Overly broad CORS lets hostile sites act with a user's session.
  • Client → product API → AI provider, with server-side guardrails. Any key used in the browser can be extracted and abused.
  • Prompt/model changes gated by an eval suite. AI behaviour changes with prompts, models and data; evals are its regression tests.
